# Empório da Música — Customer Support Agent

> 🇧🇷 [Versão em português](README_PT.md)

Prototype of a text-message customer support agent for **Empório da Música**, a musical instrument store
in Campo Grande/MS, Brazil. The virtual assistant, **Lia**, answers customers in Portuguese in the
store's tone ("informal but professional"). She looks up the catalog, promotions and orders in real time,
applies the store's policy manual and declines out-of-scope topics.

> The agent talks to customers in **Portuguese**, because it serves a Brazilian store. That is why the
> example conversations, the curated policy file and the system prompt are in Portuguese, while this
> documentation is in English.

## How to run

Prerequisites: Python ≥ 3.11 and [uv](https://docs.astral.sh/uv/). You also need an Anthropic API key.

```bash
uv sync                                  # creates .venv and installs dependencies
cp .env.example .env                     # then fill in ANTHROPIC_API_KEY
uv run emporio-agent chat                # ephemeral conversation
uv run emporio-agent chat --session ana  # history persisted in .sessions/ana.json
```

Inside the chat, `/nova` restarts the conversation and `/sair` exits. `--trace file.jsonl` records every
tool call, which helps with debugging.

| Variable | Default | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | credential (required) |
| `EMPORIO_MODEL` | `claude-opus-5-5` | model |
| `EMPORIO_EFFORT` | `low` | reasoning depth (`low` … `max`) |
| `EMPORIO_SESSIONS_DIR` | `.sessions` | where conversation histories are stored |
| `EMPORIO_NOW` | real clock | freezes the store's "now" (ISO 8601 with offset); used by the tests |
| `EMPORIO_JUDGE` | on | `off` disables the LLM judge in the E2E suite (cheaper runs) |
| `EMPORIO_JUDGE_MODEL` | `claude-sonnet-5-5` | judge model, different from the agent's model |

### End-to-end tests

```bash
uv run pytest tests/e2e -v
```

The suite runs the **real CLI**, as a subprocess, against the **real LLM**. Each run produces a verifiable
artifact:

- `reports/e2e/latest/report.md` and `report.json`: every scenario, every check with its detail
  (pass/fail), the judge's scores with justification, the tools called with their arguments, the model
  and the simulated clock.
- `reports/e2e/latest/transcripts/*.md`: the full conversation of each scenario.
- `examples/*.md`: the example conversations, regenerated by the suite itself.

A full run takes about 5 minutes. It makes paid API calls: the agent's 20 conversations plus one judge
evaluation per scenario. `EMPORIO_JUDGE=off` makes it cheaper. Without `ANTHROPIC_API_KEY`, the suite is
skipped with a message explaining why.

## Architecture

```
 customer ─► cli.py ─► agent.py ◄────── Anthropic Messages API (Claude)
                          │  tool use loop
                          ▼
                       tools.py ─► store/catalog.py   cleaned, typed CSVs
                                 ─► store/pricing.py   promotion, PIX, installments (Decimal)
                                 ─► store/policies.py  knowledge/politicas_da_loja.md by topic
                                 ─► store/hours.py     open/closed in Campo Grande's time zone
 history.py (JSON sessions)   tracing.py (JSONL)
```

Tools exposed to the model:

| Tool | When the model uses it |
|---|---|
| `buscar_produtos` | search by term, category and price range ("acoustic guitars up to R$ 1000") |
| `detalhar_produto` | price, stock, specs and alternatives for a specific item |
| `consultar_pedido` | status, items and tracking. Requires the order number **and** the e-mail or phone of its customer |
| `consultar_politica` | returns, warranty, payment, shipping, hours, contact, privacy, scope |
| `status_loja` | current date and time in Campo Grande; open or closed; next opening |

The contract between modules is in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Failure modes were
mapped before any code and are in [`docs/FAILURE_MODES.md`](docs/FAILURE_MODES.md) (both in Portuguese).

## Technical decisions

**Approach: function calling, no framework.** The store's questions fall into two kinds.
- **Structured data** questions (price, stock, orders) need exact filtering, not semantic similarity:
  "acoustic guitars up to R$ 1000" is a `WHERE` clause.
- **Policy** questions, answered by a short document.

So each need became a typed tool, and the model decides which one to call. I used the official Anthropic
SDK with a short manual loop, without LangChain or similar. That keeps every message and tool call
visible (JSONL trace) and leaves no abstraction layers to debug. I ruled out a SQL agent: it gives the
model too much freedom over customer data (LGPD, Brazil's data protection law) and makes price
calculations non-deterministic.

**Arithmetic lives in code, not in the LLM.** Promotional prices, the PIX discount and the maximum
interest-free installments are computed with `Decimal` and returned already formatted ("R$ 2.089,05").
The manual says wrong price information "may constitute false advertising", so these numbers cannot be
left to the model. Rules enforced in code:
- the 5% PIX discount does not stack with a promotion (manual §6.2);
- only promotions with `is_active = 1` affect the price;
- installments follow the minimum-installment tiers of §3.1.

For the same reason, the order lookup already returns how many days have passed since the purchase and
since the estimated delivery, so the exchange and withdrawal deadlines do not depend on date arithmetic
done by the model.

**Policy retrieval: sections by topic, no embeddings.** The manual is 8 pages long (≈3k tokens).
Automatic PDF extraction scrambles its tables: the opening-hours table becomes unreadable. So I wrote a
curated markdown version (`knowledge/politicas_da_loja.md`), one section per topic, and the
`consultar_politica(topico)` tool returns the requested section. This is deterministic, auditable and has
no risk of retrieving the wrong chunk. With hundreds of documents, I would switch to hybrid search
(BM25 + embeddings) behind the same tool interface.

**Model: Claude Opus 5.5 with `effort: low`.** Customer support is a conversation and tool-routing task.
Low effort gives short, fast answers while keeping the most capable model deciding when to look up data
and when to look up policies. Model and effort are configurable through environment variables. I also
configured:
- *prompt caching*: the system prompt and tools are static, and the current time comes from the
  `status_loja` tool rather than the prompt, so the cache is not invalidated;
- server-side refusal *fallback*.

**Prompt strategy.** The system prompt defines the persona and tone from manual §7.1. It contains the
rules for when to use each tool, for example "never state a price, stock level or deadline without
checking the system in this turn". It also sets the scope: instruments only, with accessories redirected
and unrelated topics declined. Tool descriptions reinforce *when to use* each tool, because they are what
drives routing.

**Privacy (LGPD).** `consultar_pedido` only returns data if the e-mail or phone matches the customer of
**that** order. Phones are compared by digits only, with or without area code. The error is identical for
"order does not exist" and "contact does not match", so order numbers cannot be enumerated. There is also
no customer search by name: the data has namesakes and one duplicated e-mail.

**Interface: CLI.** The challenge is about the agent. The CLI reads stdin line by line, so it works both
in a terminal and through a *pipe*, which lets it be tested end to end with no mocks.

**Persistence: one JSON file per session.** With `--session`, the history is saved after every turn,
with atomic writes. Customers can come back later and continue the conversation. The history is
*append-only*, as the API requires for the model's reasoning blocks. If the API fails mid-turn, the turn
is rolled back and the history stays valid.

**Tests: E2E only, in two layers.** There are no unit tests. Twenty scenarios talk to the real CLI. They
cover catalog, prices, orders, policies, scope, privacy and prompt injection.

1. **Objective checks** on **facts** and **the tool trace**, not on wording. For example: was the right
   tool called? Does the price 2,199 appear? Was the inactive 12% promotion left out? Did no customer data
   leak during the injection attempt?
2. **LLM as a judge.** A model different from the agent's (`claude-sonnet-5-5`, with structured output)
   reads each conversation, including tool outputs, and scores it from 1 to 5 with a justification. The
   criteria are **tone** (manual §7.1), **courtesy**, **clarity** and **faithfulness** to the tools. The
   minimums are 3 for the first three criteria and 4 for faithfulness.

The judge caught what the objective checks miss: subtle hallucinations alongside correct facts. For
example, describing a product the store does not carry, inventing a "confirmation e-mail" the policy does
not mention, inferring prices beyond the results shown, or promising that the team "will investigate".
Each finding became a fix in the prompt or in a tool. The full price range, for instance, is now returned
by the search.

The thresholds were never lowered, but the judge's rubric was calibrated three times, after reading
transcripts where it penalized something legitimate. Each calibration clarified that these are not
fabrications:
- naming instrument types as examples;
- directing the customer to the team's official channels;
- describing what Lia's own tools can do.

To tell calibration apart from loosening, every low faithfulness score was checked against the exact
sentence quoted by the judge.

The store clock is frozen per scenario (`EMPORIO_NOW`), which makes date-dependent cases, such as the
right of withdrawal, reproducible.

### Data handling

| Finding | Decision |
|---|---|
| Active product with stock 0 (Giannini GF-3D) | availability derived from status **and** stock: shown as `esgotado` (sold out) and the agent suggests alternatives |
| `discontinued` products (with stock > 0) and `coming_soon` | status overrides stock and the product is not offered as available |
| Several promotions for the same product, most of them inactive | only `is_active = 1` counts; if more than one is active, the largest discount wins |
| Takamine GD20 with an **inactive** 12% promotion | ignored, as §7.3 requires ("never promise a discount that is not in effect") |
| Order total different from the sum of its items (orders 3 and 20) | the order total is historical and is the one reported |
| Empty fields in orders (tracking, estimated delivery) | treated as absent, never as empty text |
| Product and category names with different accents, case or abbreviations ("gd 20", "violao") | normalization (accent removal and token matching) |
| "Cordas" may mean the Orchestral Strings category or the accessory (guitar strings) | the prompt treats "cordas" alone as the accessory, which the store does not sell |

### Assumptions about the policy manual

The manual contradicts itself. Each resolution below is noted as a "Nota de curadoria" (curation note) in
the curated file.

- **Opening hours:** the PDF table is misaligned. I adopted Mon–Fri 9am–6pm, Sat 9am–1pm, closed on
  Sundays and holidays, the only consistent reading.
- **Phone:** the header and the "Telefone / WhatsApp" table say (67) 3341-4444. §7 cites
  (67) 3321-4500. I adopted the former, which appears twice and with an explicit label. In real life this
  would be confirmed with the store's management.
- **E-mail:** the spelling "empóriodamusica" is a typo. I adopted `contato@emporiodamusica.com.br`.
- **Installments:** the table states a minimum installment of R$ 100, but §3.1 details tiers (up to 3x
  with no minimum; 4–6x with installments ≥ R$ 80; 7–12x with installments ≥ R$ 100). The more specific
  rule prevails. Purchases under R$ 50 cannot be paid in installments.
- **Receipt date:** the data has no actual delivery date. For the 7-day withdrawal period (counted from
  receipt), the agent uses the estimated delivery date as the reference and tells the customer so.

## Known limitations and next steps

- **Holidays** are not modeled in the store's hours. The next step would be a holiday calendar for
  Campo Grande/MS.
- **Shipping:** the agent explains the rules but does not compute the cost by ZIP code, since the data
  has no shipping table.
- **Complaints** are acknowledged and routed to the phone or e-mail, but not recorded. With more time, I
  would add a `registrar_reclamacao` tool with a ticket number and the 24-business-hour SLA.
- **Evaluation:** the suite covers 20 hand-written scenarios. With non-deterministic answers, a scenario
  occasionally flips between runs. The next step would be to run each scenario N times and report the
  pass rate, and to grow the set with real customer questions from WhatsApp.
- **Channel:** the manual names WhatsApp as the main channel. `Agent` does not depend on the CLI, so
  plugging in a webhook (FastAPI + WhatsApp Business API) would be a new interface layer.
- **Catalog scale:** for thousands of products, the in-memory search would move to SQLite/Postgres with a
  text index, behind the same tool.

## Use of AI coding assistants

The project was built with **Claude Code** (Claude Opus 5.5), in an **agent orchestration** workflow.
The roles were clearly split: I orchestrated the work and organized the entire foundation the agents
needed; Claude Code, as an orchestrator agent plus subagents, carried out the execution.

### My role: orchestration and the agent's foundation

- **Organizing the foundation.** I prepared the ground the agents worked on: the store data (CSVs and
  policy manual), the challenge brief and my development rules, so that every agent started from the same
  context and the same criteria.
- **Working rules.** I defined the standards that guided the whole execution:
  - **E2E tests only**, ending in a verifiable, repeatable artifact;
  - **failure modes written before** the code;
  - **parallel agents**, each on disjoint files, bound to a contract;
  - **clean code**.
- **Orchestration.** I drove the stages, followed every delivery, requested reviews and extensions (such
  as growing the suite and adding the LLM judge) and decided when each stage was ready to move on.

### Claude Code's role: execution

| Stage | What was done |
|---|---|
| **1. Discovery and contract** | The orchestrator read the brief, the CSVs and the PDF, mapped the data inconsistencies and wrote the contract between modules (`docs/ARCHITECTURE.md`). The failure modes (`docs/FAILURE_MODES.md`) came **before** any code. |
| **2. Parallel implementation** | Three subagents at the same time, on disjoint files: **(a)** data, pricing, curated policies and tools; **(b)** agent loop, persona, persistence and CLI; **(c)** E2E suite with report. Each one received expected values to check against (e.g. "Takamine GD20 → R$ 2.199,00; PIX R$ 2.089,05; 12x R$ 183,25"). |
| **3. Integration and review** | The parts were integrated, the prompt and the loop reviewed, and a fourth agent did a correctness and clean-code review. |
| **4. Validation** | The E2E suite runs the real CLI against the real model and generates the example conversations in this repository. |
| **5. Suite extension** | The suite grew from 9 to 20 scenarios and gained the LLM judge. The new failure modes (E1–E11, J1–J3) were written first; then two parallel subagents wrote the scenarios and the judge. |

### How failures were handled

Every suite failure was diagnosed from the transcript before any change:

- **the agent was wrong** → the prompt or the tool was fixed;
- **the check tested wording, not facts** → the check was fixed;
- **the judge's score thresholds were never lowered.**

The technical decisions are documented above with the rationale for each one, so they can be audited:
tool routing, order verification for LGPD, curation of the manual's contradictions and arithmetic in
code. The commit history reflects these stages.
